# Cyberdeck Handheld Project

## 1. プロジェクト概要

Linux系の携帯エミュレーターゲーム機をベースに、ゲームだけでなく、スクリプト実行、SSHによる遠隔開発、Androidによるブラウザ閲覧ができる多目的携帯端末を製作する。

通常時はコントローラーだけで操作できるゲーム機として使用し、必要に応じてキーボード・マウス・外部ディスプレイを接続することで、小型のLinux開発端末として利用できるようにする。

### 仮称

**Cyberdeck Handheld**

別案：

- Pocket Deck
    
- GameShell Terminal
    
- ControlDeck
    
- Handheld Workstation
    
- DeckBoy
    
- Gopher Deck
    

---

## 2. コンセプト

> 普段は携帯ゲーム機。  
> ボタン操作でLinuxのアクションを実行でき、周辺機器を接続すると開発端末に変形する。

本端末は、小型PCを無理に携帯ゲーム機化するのではなく、既製のLinux携帯ゲーム機を基盤として利用する。

これにより、以下を最初から確保する。

- 液晶画面
    
- バッテリー
    
- 十字キー
    
- アナログスティック
    
- ABXYボタン
    
- スピーカー
    
- Wi-Fi
    
- 携帯できる筐体
    
- ゲーム用の基本ソフトウェア
    

その上に、Linux端末としての機能を追加する。

## 3. 主要機能

### 3.1 エミュレーターゲーム機能

通常の携帯ゲーム機として、所有するゲームソフトから適法に用意したデータをエミュレーターで動作させる。

想定対象：

- ファミリーコンピュータ
    
- スーパーファミコン
    
- ゲームボーイ系
    
- PlayStation
    
- 一部のNintendo 64
    
- 対応性能によってはPSP、Dreamcastなど
    

使用候補：

- RetroArch
    
- EmulationStation
    
- 独立エミュレーター
    
- Linux携帯機向けディストリビューション
    

### 必須条件

- 本体ボタンだけでゲームを選択・起動できる
    
- スリープまたは安全な終了ができる
    
- ゲーム終了後にメニューへ戻れる
    
- セーブデータをバックアップできる
    
- ゲーム機能と追加したLinux機能が干渉しない
    

---

### 3.2 コントローラー式アクションランチャー

キーボードがなくても、登録されたLinux操作やスクリプトをコントローラーから選択して実行できるようにする。

仮称：

**Action Deck**

### 基本操作

|入力|動作|
|---|---|
|十字キー・左スティック|項目選択|
|A|決定・実行|
|B|戻る・キャンセル|
|X|実行結果や詳細を表示|
|Y|お気に入り登録|
|L・R|カテゴリー切り替え|
|START|メインメニュー|
|SELECT長押し|どの画面からでもランチャーを開く|

### アクション例

#### System

- IPアドレスを表示
    
- バッテリー残量を表示
    
- CPU温度を表示
    
- ストレージ容量を表示
    
- Wi-Fi再接続
    
- 再起動
    
- シャットダウン
    

#### Remote

- 自宅PCへの接続確認
    
- 自宅PCへSSH接続
    
- ロボットPCへSSH接続
    
- Tailscale接続
    
- Moonlight起動
    
- リモートデスクトップ起動
    

#### Development

- Gitリポジトリを更新
    
- Obsidian Vaultを同期
    
- 開発環境の状態を確認
    
- tmuxセッションへ接続
    
- Neovimを起動
    
- Gitの差分を表示
    

#### Robot

- ロボットPCへの疎通確認
    
- ROS 2ノード一覧を取得
    
- ROS 2トピック一覧を取得
    
- systemdサービスの状態確認
    
- rosbag記録開始
    
- rosbag記録停止
    
- ログ表示
    

危険なロボット動作や非常停止については、単純なワンボタン操作にせず、通信切断や誤操作を考慮した専用設計を行う。

### 3.3 SSH開発モード

外部ディスプレイとキーボードを接続し、自宅PC、大学PC、ロボット搭載PCなどへSSH接続する。

```text
携帯ゲーム機
├─ HDMI → 外部ディスプレイ
├─ USB/Bluetooth → キーボード・マウス
└─ Wi-Fi → SSH接続先
                 ├─ 高性能PC
                 ├─ 開発サーバー
                 └─ ロボットPC
```

### 開発方式

端末本体で重い処理を実行するのではなく、基本的には接続先PCで実行する。

端末側：

- SSHクライアント
    
- tmux
    
- Git
    
- Neovim
    
- ファイル確認
    
- 軽いPythonスクリプト
    
- ログ閲覧
    
- ネットワーク診断
    

接続先：

- VS Code
    
- Codexなどの開発ツール
    
- Docker
    
- ROS 2
    
- Webots
    
- ビルド
    
- テスト
    
- 大規模なコンパイル
    

### 想定操作

```bash
ssh desktop
tmux attach
cd ~/project
nvim .
```

あるいはAction Deckから、

```text
Development
└─ 自宅PCの開発セッションを開く
```

を選ぶだけで、SSHとtmux接続を自動実行する。

```text

画面：本体液晶
OS：Linux
用途：ログ閲覧、SSH、短いコマンド
```

長文入力や本格的なコーディングは対象外とする。

```text
入力：物理キーボード・マウス
画面：HDMI外部ディスプレイ
OS：Linux
用途：SSH、tmux、Neovim、遠隔開発
```

端末を簡易ドックへ接続し、PCに近い形で使用する。

---

### モードE：ブラウザモード

```text
入力：キーボード・マウスまたは本体コントローラー
画面：本体液晶またはHDMI
OS：Android
用途：Web閲覧、Androidアプリ
```

Linux側で無理に重量級ブラウザを動かすのではなく、Android側に役割を分担する。

## 5.2 Action Deckの構成

```text
ゲームパッド入力
        ↓
Controller Daemon
        ↓
Action Deck UI
        ↓
アクション設定ファイル
        ↓
Shell / Python / SSHコマンド
        ↓
実行結果表示
```

### 実装候補

- Python
    
- pygame
    
- evdev
    
- subprocess
    
- YAML
    
- systemd user service
    

### 設定ファイル例

```yaml
categories:
  - name: Remote
    actions:
      - name: 自宅PCの状態確認
        command:
          - ping
          - -c
          - "1"
          - desktop.local
        timeout: 5

      - name: 自宅PCへSSH
        command:
          - ssh
          - desktop

  - name: Development
    actions:
      - name: Obsidianを同期
        command:
          - /home/deck/scripts/sync-obsidian.sh

      - name: tmuxへ接続
        command:
          - ssh
          - -t
          - desktop
          - tmux attach-session -t main

  - name: System
    actions:
      - name: IPアドレス表示
        command:
          - /home/deck/scripts/show-ip.sh
```

文字列全体をシェルに渡す方式は、コマンドインジェクションや引用符の問題が起きやすい。そのため、可能な限りコマンドと引数を配列として管理する。

## 5.3 外部画面

HDMI端子の存在だけではなく、以下を確認する。

- 1280×720以上を出力できるか
    
- 本体画面の単純拡大だけではないか
    
- Linux側で解像度を変更できるか
    
- Android側でもHDMI出力できるか
    
- HDMI接続中にUSB入力を利用できるか
    
- HDMI接続状態で正常に起動できるか
    
- 音声の出力先を選択できるか
    

### 目標解像度

- 最低：1280×720
    
- 推奨：1920×1080
    
- 携帯画面：640×480以上
    

本体SoCの負荷と文字の読みやすさを考えると、開発モードはまず720pで安定させる。

## 5.4 USB構成

理想的には、以下を同時に利用できる必要がある。

- 本体への充電
    
- USBキーボード
    
- USBマウス
    
- USBメモリ
    
- 必要に応じて有線LAN
    

そのため、購入前に次を確認する。

- USB-C端子が2個以上あるか
    
- 充電端子とOTG端子が分かれているか
    
- OTG使用中にも充電できるか
    
- USBハブが利用できるか
    
- USB PDが必要か
    
- Bluetoothキーボードが安定するか
    

### 理想構成

```text
端子1：電源入力
端子2：USB OTGハブ
Mini HDMI：外部ディスプレイ
```

USB-C端子が1つしかない機種では、給電とOTGの同時利用が難しい可能性がある。

## 6. ハードウェア選定条件

ベース機は、価格やゲーム性能だけで選ばず、以下を重視する。

### 必須条件

- Linuxが動作する
    
- Androidが動作する、またはAndroid版が存在する
    
- HDMI出力
    
- Wi-Fi
    
- USBキーボード対応
    
- SSHクライアントを利用可能
    
- microSDからOSを起動可能
    
- コントローラー入力をLinuxから取得可能
    
- 改造情報やコミュニティが存在する
    

### 推奨条件

- RAM 4GB以上
    
- 64bit ARM
    
- 独立した充電端子とOTG端子
    
- Bluetooth
    
- 5GHz Wi-Fi
    
- H.264/H.265ハードウェアデコード
    
- バッテリー交換が比較的容易
    
- Mini HDMIまたはMicro HDMI
    
- メインラインLinuxに近い環境
    
- DebianやUbuntu系環境を構築可能
    

### 避けたい条件

- OSイメージがメーカー独自で更新されない
    
- Linux部分が強く読み取り専用化されている
    
- HDMIがゲーム画面のミラーリング専用
    
- USB OTG使用中に充電できない
    
- Android側にGoogle Playが導入できない
    
- コントローラー入力が独自ドライバに依存する
    
- 分解情報が少ない
    
- RAM 1GBのみ

## 7. 開発方針

## 7.1 既製品を壊さずに始める

最初から筐体加工や基板改造を行わない。

初期段階では以下だけを使用する。

- ベースゲーム機
    
- microSDカード
    
- Mini HDMIケーブル
    
- USB OTGアダプター
    
- 一般的なキーボード
    
- マウス
    
- モニター
    

ソフトウェア機能を完成させてから、着脱式キーボードや専用ドックを製作する。

---

## 7.2 ゲーム機能を最優先で維持する

追加機能によって、元のゲーム機としての使いやすさを失わないようにする。

- 通常起動ではゲームメニューを表示
    
- Action Deckは明示的な操作で起動
    
- デスクトップ環境を常時起動しない
    
- バックグラウンドサービスを最小限にする
    
- バッテリー消費を増やさない
    
- ゲームパッド入力の競合を避ける
    

---

## 7.3 コントローラーのみで基本操作を完結させる

Action Deck内では、マウスカーソルをコントローラーで動かす方式よりも、ゲーム機らしい項目選択UIを優先する。

```text
良い例：
十字キーで選択 → Aで実行

避けたい例：
スティックで小さなマウスカーソルを動かす
```

マウスエミュレーションは、ブラウザや一般GUIを操作するときの補助機能として扱う。

---

## 7.4 重い処理はリモートへ逃がす

本体は高性能PCの代替ではなく、操作端末として設計する。

```text
本体が担当
├─ 入力
├─ 表示
├─ 接続
├─ 軽いスクリプト
└─ ローカルゲーム

遠隔PCが担当
├─ コンパイル
├─ Docker
├─ ROS 2
├─ AIツール
├─ シミュレーション
└─ 大規模処理
```

この分離によって、本体性能が低くても実用的な開発環境を実現する。

---

## 7.5 設定駆動で拡張する

Action Deckにアクションを追加するたびにプログラムを書き換えない。

- YAMLまたはJSONでアクション定義
    
- アイコン、名前、コマンド、確認方法を設定
    
- カテゴリーを自由に追加
    
- ショートカットを設定可能
    
- 実行ログを保存
    

---

## 7.6 復旧可能な構成にする

実験的な改造で起動不能になることを考え、復旧を容易にする。

- 純正OS用microSDを保存
    
- 改造用microSDを分離
    
- 設定をGit管理
    
- セーブデータを定期バックアップ
    
- OSイメージを保存
    
- 本体内蔵ストレージはなるべく変更しない
    

---

## 8. セキュリティ方針

### SSH

- パスワードログインよりSSH鍵を使用
    
- 秘密鍵には適切な権限を設定
    
- 接続先ごとにユーザーを分ける
    
- rootで直接接続しない
    
- 必要に応じてTailscaleやWireGuardを使用
    
- 公衆Wi-Fi上で不要なサービスを公開しない
    

### Action Deck

- 任意の文字列を直接シェル実行しない
    
- アクション定義の編集権限を制限
    
- `sudo`が必要な操作を最小限にする
    
- 再起動や削除操作は確認を挟む
    
- 実行時間の上限を設定する
    
- 実行履歴とエラーを記録する
    

### ロボット操作

- 状態確認系と動作指令系を分離する
    
- 通信切断時の挙動を定義する
    
- 危険なアクションは長押し・二段階確認
    
- 非常停止を通常のSSHコマンドだけに依存させない
    
- UI上で接続先ロボットを明示する

開発範囲が膨張しないよう、初期版では次を対象外とする。

- ローカルでのDocker運用

- Webotsや重いIDEの実行
    
- 独自基板の設計
    
- バッテリーセルの改造
    
- 本体筐体の切断
    
- 完全自作のLinuxディストリビューション
    
- コントローラーだけでの長文入力
    
- すべてのGUIアプリのゲームパッド対応

## 14. 現時点の方針

1. **デュアルOS対応機を優先する。**
    
2. **Linuxはゲーム、アクション、SSHを担当する。**
    
3. **AndroidはブラウザとGUIアプリを担当する。**
    
4. **本体画面では専用UI、外部画面では一般的なPC操作を行う。**
    
5. **本体性能に依存する重い処理は、SSHやリモート接続先で実行する。**
    
6. **筐体改造より先にソフトウェアと周辺機器の成立を確認する。**
    
7. **Action Deckを本プロジェクト固有の中心機能とする。**
    
8. **設定ファイルによって機能を容易に追加できる構造にする。**
    
9. **ゲーム機としての安定性を損なわない。**
    
10. **故障や設定ミスから簡単に復旧できるようにする。**
