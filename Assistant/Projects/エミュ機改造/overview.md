# エミュ機改造

## プロジェクト概要

Linux系の携帯エミュレーターゲーム機をベースに、次の4つの役割を1台へまとめるプロジェクト。

1. 普通の携帯エミュレーターとしてゲームを遊ぶ
2. 本体のコントローラーだけで登録済みスクリプトや操作を呼び出す
3. キーボードと外部ディスプレイを接続し、SSH経由で開発する
4. Androidと外部ディスプレイを使い、ブラウザやGUIアプリを利用する

単に「Linuxが動くゲーム機」にするのではなく、普段はゲーム機として自然に使え、必要なときだけ携帯オペレーション端末や簡易開発端末へ変形することを目標とする。

> [!summary] 一言で表すと
> 普段はレトロゲーム機、SELECT長押しでAction Deck、周辺機器をつなぐとSSH開発端末、Androidへ切り替えるとブラウザ端末になる携帯Cyberdeck。

## このプロジェクトで実現したい体験

### 携帯時

- 電源を入れるとゲーム用フロントエンドが起動する
- 本体ボタンだけでゲームの選択・起動・終了ができる
- SELECT長押しなどで専用のアクションメニューを呼び出せる
- IPアドレス、バッテリー、温度、接続状態などを確認できる
- 自宅PCやロボットPCに対して、定型のSSH操作を実行できる
- 長文入力をせずに、よく使う操作を選択式で完結できる

### 机上利用時

- HDMIで外部ディスプレイへ720p以上を出力する
- USBまたはBluetoothでキーボード・マウスを接続する
- SSHとtmuxを使い、自宅PCや開発サーバー上の作業へ復帰する
- Neovim、Git、ログ閲覧など、端末中心の開発作業を行う
- 重いビルド、Docker、ROS 2、Webots、AIツールは接続先PCで実行する

### Android利用時

- Android側へ切り替えてブラウザを利用する
- 外部ディスプレイ、キーボード、マウスを使ってWebを閲覧する
- GitHub、技術記事、ChatGPT、Google Classroomなどを確認する
- 必要に応じてMoonlightやリモートデスクトップを利用する

## 目的

### 主目的

- 携帯ゲーム機を、ゲーム以外にも使える自分専用端末へ拡張する
- キーボードなしでもLinuxの定型操作を実行できるUIを作る
- 低性能な携帯端末と高性能な遠隔PCを役割分担させる
- 実用性とCyberdeckらしい見た目・操作感を両立する

### 副目的

- Linuxの入力デバイス、systemd、SSH、YAML設定、Python GUIを学ぶ
- 小型画面向けUIとゲームパッド操作を設計する
- 3Dプリントや簡易ドックなど、後からハードウェア拡張へ進める
- ロボコン環境の状態確認やログ取得を携帯端末から行えるようにする

## 基本方針

1. **ゲーム機としての使いやすさを壊さない**
   - 通常起動はゲームモードを基本とする
   - 常駐処理を増やしすぎず、ゲーム性能とバッテリーを優先する

2. **筐体加工より先にソフトウェアを成立させる**
   - 最初は市販のキーボード、ケーブル、USBハブを使う
   - 無改造状態で主要機能を検証してから専用ドックを作る

3. **LinuxとAndroidを役割分担する**
   - Linux: ゲーム、Action Deck、SSH、軽量スクリプト
   - Android: ブラウザ、動画、GUIアプリ、リモートデスクトップ

4. **重い処理はリモートPCへ逃がす**
   - 本体は入力・表示・接続・軽い処理を担当する
   - コンパイル、Docker、ROS 2、Webots、AI処理は遠隔PCが担当する

5. **コントローラー操作を第一級の入力方法にする**
   - 小さなマウスカーソルを無理に動かすUIではなく、項目選択式にする
   - 文字入力が必要な場面だけ仮想キーボードや外部キーボードを使う

6. **設定駆動で拡張できる構成にする**
   - アクションはYAMLまたはJSONで定義する
   - スクリプトを追加するだけでメニュー項目を増やせるようにする

7. **壊れても復旧できるようにする**
   - 純正OS用microSDと改造用microSDを分ける
   - 設定とスクリプトをGit管理する
   - セーブデータとOSイメージをバックアップする

## 利用モード

### 1. ゲームモード

- 入力: 本体コントローラー
- 画面: 本体液晶
- OS: Linux
- 用途: レトロゲーム
- 起動時の標準モードとする

必要条件:

- 本体ボタンだけでゲームを選択・起動できる
- ゲーム終了後にフロントエンドへ戻れる
- セーブデータをバックアップできる
- Action Deckと入力が競合しない

### 2. Action Deckモード

- 入力: 本体コントローラー
- 画面: 本体液晶
- OS: Linux
- 用途: 定型アクション、状態確認、遠隔操作

想定操作:

| 入力 | 動作 |
|---|---|
| 十字キー・左スティック | 項目選択 |
| A | 決定・実行 |
| B | 戻る・キャンセル |
| X | 詳細・実行ログ表示 |
| Y | お気に入り登録 |
| L・R | カテゴリー切り替え |
| START | ホームへ戻る |
| SELECT長押し | Action Deckを開く |

詳細は [[Action Deck設計]] を参照。

### 3. 携帯ターミナルモード

- 入力: 本体コントローラー、仮想キーボード
- 画面: 本体液晶
- OS: Linux
- 用途: ログ閲覧、短いSSH操作、簡単なコマンド

長文入力や本格的なコーディングは対象外とする。結果確認と定型操作を中心にする。

### 4. SSH開発モード

- 入力: 外部キーボード・マウス
- 画面: HDMI外部ディスプレイ
- OS: Linux
- 用途: SSH、tmux、Neovim、Git、ログ閲覧

想定フロー:

```text
HDMI・キーボード・マウスを接続
        ↓
開発モードを起動
        ↓
自宅PCへSSH
        ↓
tmuxの既存セッションへ接続
        ↓
Neovim・Git・各種CLIで作業
```

本体では軽い端末処理だけを行い、開発環境の本体は遠隔PCへ置く。

### 5. Androidブラウザモード

- 入力: 外部キーボード・マウス、必要に応じて本体コントローラー
- 画面: 本体液晶または外部ディスプレイ
- OS: Android
- 用途: Web閲覧、Androidアプリ、動画、GUI型リモート操作

Linuxへ重量級デスクトップブラウザを無理に載せるより、Androidのブラウザ環境を使う方針とする。

## Action Deckで想定するカテゴリー

### System

- IPアドレス表示
- バッテリー残量表示
- CPU温度表示
- ストレージ使用量表示
- Wi-Fi再接続
- 再起動
- シャットダウン

### Remote

- 自宅PCへのping
- 自宅PCへSSH接続
- LattePandaやロボットPCへSSH接続
- Tailscale接続状態確認
- Moonlight起動

### Development

- tmuxセッションへ接続
- Gitリポジトリをpull
- Git statusを表示
- Obsidian Vaultを同期
- 開発サーバーの状態確認

### Robot

- ROS 2ノード一覧取得
- ROS 2トピック一覧取得
- systemdサービス状態確認
- rosbag記録開始・停止
- ログ取得

ロボットを実際に動かす操作は、状態確認系と分離し、誤操作・通信切断・非常停止を考慮して別途設計する。

## ハードウェア要件

### 必須条件

- Linuxが動作する
- Androidが動作する、またはAndroid版が存在する
- HDMIまたはUSB-C映像出力がある
- Wi-Fiが利用できる
- USBまたはBluetoothキーボードが利用できる
- SSHクライアントを導入できる
- microSDからOSを起動・復旧できる
- Linuxから本体コントローラー入力を取得できる
- 改造・OS導入の情報が一定量存在する

### 強く推奨する条件

- RAM 2GB以上、可能なら4GB以上
- 64bit ARM
- 5GHz Wi-Fi
- Bluetooth
- 外部画面で1280×720以上を出力可能
- 充電とUSB OTGを同時利用可能
- 充電端子とOTG端子が分かれている
- ハードウェア動画デコード対応
- バッテリーやmicroSDへアクセスしやすい

### 避けたい条件

- LinuxのみでAndroidが使えない
- RAM 1GBのみ
- HDMIが低解像度ミラーリング専用
- OTG使用中に充電できない
- OSが強く読み取り専用化されている
- 本体コントローラーが独自ドライバに強く依存する
- OSイメージや復旧方法が公開されていない

詳しい比較は [[機種選定]] を参照。

## 現時点の機種方針

第一候補は **ANBERNIC RG353V**。

理由:

- LinuxとAndroidを役割分担できる構成に近い
- 縦型でCyberdeckらしい見た目になる
- 本体コントローラー、画面、バッテリー、Wi-Fiが一体化されている
- 外部画面、USB入力、SSHを組み合わせる構想と相性がよい
- 1号試作機として比較的気軽に検証できる

ただし、まだ購入決定ではない。Androidブラウザの快適性、外部出力、OTGと給電の同時利用、現在利用できるLinux OS、実機価格を確認してから決定する。

> [!warning] 型番注意
> RG353VとRG353VSは別物。今回必要なのはAndroidを利用できる構成であり、Linuxのみのモデルは要件から外れる。

## セキュリティ・安全方針

### SSH

- SSH鍵を使用する
- rootで直接ログインしない
- 接続先ごとにユーザーと権限を分ける
- 秘密鍵のファイル権限を制限する
- 外部から接続する場合はTailscaleやWireGuardを利用する

### Action Deck

- 任意文字列をそのままshellへ渡さない
- コマンドと引数を配列として扱う
- タイムアウトを設ける
- 標準出力と標準エラーを記録する
- `sudo`を必要とする操作を最小限にする
- 再起動・シャットダウン・削除系は確認操作を入れる

### ロボット操作

- 状態確認と動作命令を別カテゴリーにする
- 接続先ロボット名を常に明示する
- 危険な操作は長押しや二段階確認にする
- 非常停止をSSHやAction Deckだけに依存させない
- 通信切断時の安全動作をロボット側で保証する

## 初期版で対象外とすること

- 本体だけでの本格的なコーディング
- 本体上でのDocker運用
- 本体上でのROS 2シミュレーション
- Webotsや重量級IDEのローカル実行
- 独自基板の設計
- バッテリーセルの改造
- 初期段階での筐体切断
- 完全自作Linuxディストリビューション
- コントローラーだけでの長文入力
- 一般的な全GUIアプリのゲームパッド対応

## 主なリスク・未確認事項

| 項目 | リスク | 対応方針 |
|---|---|---|
| Androidブラウザ | RAM不足で重いWebページが遅い | 実機動画・レビュー・中古機で確認 |
| 外部画面 | ミラーリングのみ、解像度固定 | 購入前にOS別の報告を確認 |
| USB | OTG中に充電できない | 端子構成とハブ動作を確認 |
| Linux自由度 | ゲーム専用OSでパッケージ導入が難しい | Debian系環境またはコンテナ利用を検討 |
| 入力競合 | Action Deckとゲーム操作が競合 | 起動中アプリを判定し、ホットキーを限定 |
| バッテリー | 常駐処理やWi-Fiで消費増加 | 常駐サービスを最小化 |
| ロボット操作 | 誤操作や通信切断 | 状態確認中心から開始し、安全設計を別途実施 |
