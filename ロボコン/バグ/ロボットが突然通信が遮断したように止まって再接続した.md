
`exit code -13` は Linux 的には **signal 13 = SIGPIPE** で終了した、という意味です。`SIGPIPE` は「切れた通信先/pipe/socket に書き込もうとした」時に出るシグナルで、何も対策していないプロセスはその場で終了します。

今回の流れはこうです。

1. `r1.twomatch` が `map` transform を取れず警告を出していた  
   `map` frame がまだ存在せず、自己位置推定が成立していない状態です。

2. `r1.dog3_rtcl` の `geoloc` が `NotInitialized` を繰り返していた  
   これは「自己位置推定フィルタが初期化されていない」状態で、odometry/imu を入れられていません。これ自体はクラッシュ原因というより、自己位置推定が未成立な症状です。

3. 直前に `urg_node_0` が失敗している  
   ```text
   [r1.urg_node_0]: Could not grab multi echo scan.
   ```
   `urg_node_0` は `/r1` の右LiDARで、設定上は `192.168.0.10` です。

4. その直後に `sensor_container` が `SIGPIPE` で死亡  
   `sensor_container` には `urg_node_0`, `urg_node_1`, `scan_filter`, `twomatch` が同居しています。なので1個の通信系エラーがプロセス全体を巻き込んで、scan_filter/twomatch も一緒に消えました。

5. その後の Foxglove のエラーは結果  
   ```text
   Failed to retrieve parameters from node '/r1/scan_filter'
   Failed to retrieve parameters from node '/r1/urg_node_1'
   Failed to retrieve parameters from node '/r1/twomatch'
   Failed to retrieve parameters from node '/r1/urg_node_0'
   ```
   これはそれらのノードが既に死んでいるので、Foxglove bridge がパラメータ取得に失敗しただけです。

つまり原因を一言で言うと、**`urg_node_0` 周辺のLiDAR通信が不安定/切断され、その通信エラーが `SIGPIPE` として `sensor_container` 全体を終了させた**、です。

今回入れた修正は、`preloaded_component_container` 側で `SIGPIPE` を無視するものです。これにより、同じような通信切断が起きても即プロセス終了せず、通常の通信エラーとして扱えるようになります。根本原因のLiDAR通信不良そのものは別なので、再発時は `192.168.0.10` のLiDAR電源、LANケーブル、IP疎通、スイッチ/ハブ、URGドライバの状態を見るのが次の調査ポイントです。
